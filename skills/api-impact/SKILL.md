# api-impact

백엔드가 새 API 스펙을 배포했을 때, **무엇이 달라졌고 / 그게 내 코드 어디를 건드리는지**를 보고서로 낸다.

## 이 스킬이 하지 않는 것 — 먼저 읽어라

- **코드를 고치지 않는다.** 보고서만 낸다. 수정은 사용자가 별도로 지시한다.
- **경로·스크립트 이름을 하드코딩하지 않는다.** 프로젝트마다 다르므로 매번 0단계에서 발견한다.
- **변경이 없으면 "변경 없음"으로 끝낸다.** 억지로 찾아내지 않는다.
- **생성물 디렉터리 안의 파일을 직접 수정하지 않는다.** 재생성 때 날아간다.
- **임의로 커밋·스태시하지 않는다.** 작업 트리가 문제면 멈추고 보고한다.

## 인자

`$ARGUMENTS`

| 인자 | 뜻 |
|---|---|
| `--no-gen` | 재생성을 건너뛴다. 사용자가 이미 돌렸을 때 (diff부터 시작) |
| 타깃명 | orval 타깃이 여러 개일 때 하나만 (예: `fitgenieV2`, `pss`) |

인자가 없으면 전체 타깃을 재생성부터 수행한다.

---

## 0단계 — 발견 (하드코딩 금지)

이 프로젝트가 어떻게 생겼는지 **읽어서 알아낸다.**

1. orval 설정을 찾는다.
   ```
   ls orval.config.* 2>/dev/null || find . -maxdepth 3 -name 'orval.config.*' -not -path '*/node_modules/*'
   ```

2. 설정을 읽고 타깃마다 다음을 뽑는다.
   - 타깃 이름 (`defineConfig({ <타깃명>: ... })`)
   - `input.target` — **원격 URL인가 로컬 파일인가** (이게 2단계를 가른다)
   - `output.target`, `output.schemas` — diff를 볼 경로. **schemas가 따로 있으면 반드시 포함한다** (빠뜨리면 타입 변경을 통째로 놓친다)
   - `output.clean` — true면 재생성이 디렉터리를 비운다
   - `input.override.transformer` — 있으면 스펙이 가공되므로, 원본 스펙과 생성물이 1:1이 아니다

3. 실행할 스크립트를 찾는다. `package.json`의 `scripts`에서:
   - 명령에 `orval`이 들어간 스크립트
   - **그리고 그것을 호출하는 상위 스크립트도 본다.** 예: `"api:gen:refresh": "node scripts/fetch-swagger.mjs && npm run api:gen"` 는 `orval`이라는 단어가 없지만 이게 정답이다
   - **input이 로컬 파일이면 스펙을 먼저 내려받는 스크립트가 거의 항상 있다. 그걸 써야 한다.** 안 그러면 낡은 스펙으로 재생성해서 "변경 없음"이라는 거짓 결론이 나온다

4. 발견 결과를 표로 보여주고, **어느 스크립트를 돌릴지 확인받는다.**

   | 타깃 | 입력 | 출력 경로 | clean | 실행할 스크립트 |
   |---|---|---|---|---|

---

## 1단계 — 안전장치

재생성은 파일을 덮어쓴다. 그 전에 확인한다.

1. 저장소 루트 확인: `git rev-parse --show-toplevel`

2. **출력 경로만** 깨끗한지 본다. 트리 전체가 아니다 — 대부분의 저장소는 평소에 dirty하므로 전체를 요구하면 이 스킬은 못 쓴다.
   ```
   git status --porcelain -- <출력경로들> <schemas경로들>
   ```
   - 비어 있으면 진행
   - **비어 있지 않으면 멈추고 보고한다.** 미커밋 변경이 섞이면 diff가 오염되어 결론이 틀린다. 사용자가 커밋하거나 `--no-gen`으로 갈지 정하게 한다

3. 입력이 로컬 스펙 파일이고 그 파일도 git에 추적 중이면, **그 파일의 diff도 증거로 쓴다.** 생성물보다 읽기 쉬울 때가 많다.

4. `clean: true`면 "이 디렉터리를 비우고 다시 씁니다"라고 명시하고 승인받는다.

---

## 2단계 — 재생성과 diff 수집

`--no-gen`이면 이 단계의 실행을 건너뛰고 diff만 수집한다.

```
<0단계에서 정한 스크립트>
git diff --stat -- <출력경로들>     # 규모 파악
git diff -- <출력경로들>            # 상세
```

diff가 비었으면 **여기서 끝낸다.** "스펙에 변경 없음"이라고 보고한다.

diff가 수천 줄이면 `--stat`으로 변경 파일을 먼저 추리고, 파일 단위로 나눠 읽는다. 한 번에 다 읽지 않는다.

---

## 3단계 — 변경점 분류

orval `axios-functions` 출력은 오퍼레이션마다 **export 함수 하나 + 파라미터 타입**을 만든다. diff를 이 네 가지로 분류한다.

| 분류 | diff에서 보이는 모습 | 위험 |
|---|---|---|
| **추가** | 새 `export const xxx` / 새 타입 | 낮음 — 안 쓰면 그만 |
| **삭제** | 사라진 `export const xxx` / 사라진 필드 | 높음 — 쓰던 코드가 깨진다 |
| **시그니처 변경** | 인자 개수·순서·타입·옵셔널(`?`) 변경, **파라미터 위치 이동** | **가장 높음** |
| 무해 | 포맷·주석·import 순서·정렬 | 무시 |

### 시그니처 변경에서 반드시 확인할 것

**파라미터 위치 이동**(query ↔ path ↔ body)이 가장 위험하다. 타입 검사는 통과하는데 런타임에 서버가 400을 주거나 조용히 잘못된 데이터를 준다.

diff에서 이렇게 구분한다.
생성된 함수에서 이렇게 구분한다 (orval `axios-functions` 기준, 실측 확인됨).

- **path** — url 템플릿 리터럴의 `${...}` 보간
  `` url: `/class-reservations/${reservationId}` ``
- **query** — 함수 인자 `params?: GetXxxParams` + 설정 객체의 `params` 키
  `` { url: `/class-templates`, method: "GET", params } ``
- **body** — 설정 객체의 `data` 키
  `` { url: `/class-templates`, method: "POST", data: templateCreate } ``

같은 이름의 파라미터가 한쪽에서 사라지고 다른 쪽에 나타났다면 그것이 **위치 이동**이다.

`?`가 붙거나 떨어진 것(**필수 ↔ 선택**)도 시그니처 변경이다. 필수가 된 파라미터를 안 넘기는 기존 호출부는 전부 깨진다.

---

## 4단계 — 코드 영향 추적

**삭제·시그니처 변경**된 항목만 추적한다. 추가는 추적하지 않는다(아직 쓰는 곳이 없다).

각 export 이름으로 저장소를 훑되 **생성물 디렉터리는 제외한다** (자기 자신이 잡힌다).

```
grep -rn "<export이름>" --include=*.ts --include=*.tsx . \
  | grep -v node_modules | grep -v "<생성물경로>"
```

찾은 사용처에서 화면까지 역추적한다. 보통 `service`/`store`/`hooks`를 한 단계 더 타고 올라가면 페이지 컴포넌트가 나온다.

**사용처가 0건이면 그렇게 적는다.** "미사용"은 유효한 결론이고, 조치 우선순위를 낮추는 근거다.

---

## 5단계 — 보고

기본은 대화에 표로 낸다. 파일로 남기라고 하면 저장소에 이미 있는 API 문서 포맷을 따른다(예: `docs/api-usage-audit.md`). 새 포맷을 발명하지 않는다.

### 요약

> 타깃 N개 재생성 · 추가 A · 삭제 D · 시그니처 변경 S · 영향받는 화면 M개

### 조치 필요 (삭제 · 시그니처 변경)

| 엔드포인트 | 변경 | 사용처 | 화면 | 조치 |
|---|---|---|---|---|
| `getClassTemplates` | branchId: path → **query** | `class.service.ts:42` | 수업목록 | 호출부 수정 |

### 추가된 엔드포인트

| 엔드포인트 | 메서드 · 경로 | 대응하는 기존 API |
|---|---|---|

대응하는 기존 API가 있으면 적는다 — v1→v2 전환처럼 "무엇을 대체하는가"가 핵심 정보다.

### 무해

한 줄로 요약한다. 나열하지 않는다.

---

## 효율 계획

- 0단계 발견 결과는 세션 안에서 재사용한다. 두 번 찾지 않는다
- `git diff`는 `--stat` 먼저. 전문을 무턱대고 읽지 않는다
- 4단계 grep은 **삭제·시그니처 변경 항목에만** 돈다
- 무해 변경은 분류만 하고 본문에 나열하지 않는다

## 정지 규칙

다음 중 하나면 즉시 멈추고 보고한다.

- orval 설정을 못 찾음 → 이 스킬의 대상이 아니다
- 출력 경로에 미커밋 변경이 있음 → diff가 오염된다
- 재생성 스크립트가 실패함 → 실패 출력을 그대로 보여준다. 부분 결과로 추측하지 않는다
- diff가 비어 있음 → "변경 없음"으로 종료
